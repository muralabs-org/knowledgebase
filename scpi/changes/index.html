    Changes by release¶

    JP150PCB 1.3PCB 1.42026-11-11Jan PřibyslavskýThis page does not apply to the product or PCB revision chosen in the header.

    Download the PDF referenceJP150 SCPI Command Reference, revision 1.2 · 4.0 MB

    What changed in the control interface from one release to the next: the commands added and removed, taken from the firmware's command tables, and the behaviour changes that host software must handle. 26.6.2 is the oldest release documented here; its 108 commands are the baseline.

    26.11.0 (since 26.10.1)¶

    0 commands added, 0 removed, 0 behaviour changes.

    26.10.1 (since 26.8.0)¶

    • DSP:AUTOLOAD?: Automatic DSP program load setting (replaced by the self boot)
    • DSP:AUTOLOAD: Set the automatic DSP program load (replaced by the self boot)
    • BT:BOOTROLE?: Stored TWS boot role (replaced by BT:TWS:FALLBACKROLE?)
    • BT:BOOTROLE: Set the stored TWS boot role (replaced by BT:TWS:FALLBACKROLE)

    Behaviour changes

    1. SYS:BOOTLOADER answers SYS:BOOTLOADER:OK after at most 1 s (pending settings are written first) and restarts the module into the bootloader's update mode: the serial port disappears and a DFU device 16D0:15B7 appears. The ST ROM bootloader is no longer used. Without an update the module returns to its firmware after 5 minutes.
    2. *RST still answers Resetting device... first, then writes pending settings (at most 1 s) and resets at least 100 ms after the answer, so the answer now also arrives over USB.
    3. *IDN? reports the serial number of the factory record as its third field, N/A without a record. On a provisioned module the setter SYS:BOARD:ID answers SYS:BOARD:ID:LOCKED and writes nothing.
    4. On a module without a supported factory record every command outside the reduced set answers ERR:BOARD:UNSUPPORTED, one line without a prefix. The reduced set is marked with a dagger in the reference.
    5. New prefixes of longer commands: BT:TWS:PAIR (:START, :STATUS?), BT:TWS:SCAN? (:COUNT?, :ITEM?, :DIAG?), SYS:BOOTLOADER (:INFO?), SYS:NVM:EEPROM:STATE? (:PENDING?) and SYS:TRIG? (:MODE?, :TARGET?, :PRIORITY?). A response matcher that works by prefix must exclude the longer forms.
    6. SYS:BOOTLOADER:INFO? and SYS:NVM:EEPROM:PENDING? are extensible: later firmware may append fields. Hosts read the fields they know and ignore further ones.
    7. BT:TWS:UNPAIR answers BT:TWS:UNPAIR:OK or :ERR:MODULE; it was silent. BT:TWS:PAIR still blocks the control interface for up to 15 s: use BT:TWS:PAIR:START and poll BT:TWS:PAIR:STATUS?.
    8. BT:TWS:FALLBACKROLE? answers Standalone, Primary or Secondary; the removed BT:BOOTROLE? answered Master and Slave. The numeric values of the setter are unchanged.
    9. SYS:MEAS:VOLT? and SYS:MEAS:CURR? keep their format. On PCB 1.4 they draw no answer when the power monitor cannot be read.
    10. DSP:PC:ADVANCING? keeps its name and answer, but now reports 1 while the DSP core runs or sleeps between samples, from one status register. It used to sample the program counter, which also moves while no program runs.
    11. The virtual COM port enumerates under USB 16D0:15B8 (was 0483:5741), update mode under 16D0:15B7. Software that finds the module by VID and PID must add the new identifiers.
    12. The settings-memory layout changed (version 3 to 6). On the first start of 26.10.1 the stored settings are rebuilt once: SYS:NVM:EEPROM:STATE? answers NODATA on that start, and the input enable mask, the automatic power-down and the new settings return to their defaults; volumes, the selected input and the TWS fallback role are kept.
    13. BT:AT is unfiltered: it will send AT+RESTORE (factory reset of the Bluetooth module) or AT+BAUD (breaks the link). A development aid, not a product feature.

    26.8.0 (since 26.7.0)¶

    13 commands added, 0 removed, 6 behaviour changes.

    Added

    Command Group Function Parameter
    SYS:INPUT:ENABLE? SYS:INPUT Whether an input is enabled <source>
    SYS:INPUT:ENABLE SYS:INPUT Enable or disable an input <source>,<0|1>
    SYS:INPUT:ENABLE:LIST? SYS:INPUT The enabled inputs in one answer –
    SYS:I2C:GUARD? SYS:I2C:GUARD A second master is active on the DSP bus –
    SYS:I2C:GUARD:COUNT? SYS:I2C:GUARD Programmer episodes since start –
    SYS:I2C:GUARD:STUCK? SYS:I2C:GUARD A bus line is held low (hardware fault) –
    SYS:POWER:AUTO:MODE? SYS:POWER Level entered after the silence delay –
    SYS:POWER:AUTO:MODE SYS:POWER Set the level entered after the silence delay PWRSTAGE_IDLE, PWRSTAGE_OFF, SLEEP, STANDBY
    SYS:POWER:AUTO:DELAY? SYS:POWER Silence delay in seconds –
    SYS:POWER:AUTO:DELAY SYS:POWER Set the silence delay 10..65535
    SYS:POWER:AUTO:THRESHOLD? SYS:POWER Level above which audio counts as present –
    SYS:POWER:AUTO:THRESHOLD SYS:POWER Set the silence threshold <raw>
    SYS:POWER:AUTO:STATE? SYS:POWER Automatic power-down status and countdown –

    Behaviour changes

    1. SYS:INPUT answers SYS:INPUT:OK, :ERR:DISABLED or :ERR:PARAM, where it was silent. Software written against the old behaviour pairs this reply with the next query and drifts out of step. SYS:INPUT? may answer NONE.
    2. SYS:POWER:AUTO defaults to disabled and drives real behaviour; before it was a stored value without effect, defaulting to enabled.
    3. SLEEP no longer removes power from the Wi-Fi module; check for STANDBY when deciding whether Wi-Fi is reachable.
    4. SYS:INPUT, SYS:I2C:GUARD? and SYS:POWER:AUTO became prefixes of longer commands.
    5. SYS:I2C:GUARD? returning 0 is not proof that the bus is free; read it together with SYS:I2C:GUARD:STUCK?.
    6. DSP:INPUTMUX:* is deprecated in favour of DSP:IPAT:SETBLOCK; it still works but bypasses the DSP's parameter engine.
